# Phase 4.4 pre-alpha security review

Scope: application code, migrations, dependency lockfile, deployment entrypoints, isolated real PostgreSQL tests, TLS browser forwarding fixture and production-container checks. This is a targeted application/abuse review, not a penetration-test certification. No live Railway environment or player database was accessed. Provider assertions below require the owner's authenticated verification.

## Verified application protections

### Authentication, sessions and browser boundary

- Argon2id hashes use the existing parameters (19 MiB memory, two iterations, parallelism one). Passwords are 12–128 characters; existing hashes/passwords are not rehashed/reset by migration. No development credential is committed or logged.
- Random 256-bit session tokens are stored as SHA-256 hashes; CSRF is a separate random 256-bit session-bound value. Cookies are host-only, `HttpOnly`, `SameSite=Lax`, `Secure` for production HTTPS. Existing 30-day absolute and seven-day idle session limits remain.
- Login/registration rotate the session; logout deletes the authenticated session and replaces it with an anonymous session. PostgreSQL persistence survives process/container replacement; no memory-only session secret is introduced.
- Invalid login messages are uniform, including missing/disabled accounts; unknown users exercise a dummy Argon2 hash. Registration duplicate errors no longer explicitly state an account exists. **Successful registration versus failure can still imply username availability**; public character identity and this behavior are not a full account-enumeration solution.
- Every mutating browser/API action requires a valid session CSRF token. Strict canonical `APP_ORIGIN` validation remains; hostile/opaque Origins fail. The existing narrowly checked Codespaces localhost rewrite requires canonical Referer and Fetch Metadata and is not enabled by spoofed forwarding headers on Railway.
- `trustProxy:false` remains. Request Host/forwarded headers cannot select the trusted origin or make a production cookie insecure. Production entrypoints require explicit HTTPS `APP_ORIGIN` and a valid database URL. Environment variables override `.env`, and the runtime image contains no `.env`.
- Helmet/CSP restrict scripts, styles, images, forms and framing to the intended origin; EJS text is escaped. Native POST forms and external-origin/CSRF rejection are tested through real HTTPS termination to an HTTP backend. Tests simulate the documented forwarding behavior; they do not log in to the owner's actual Codespace/Railway service.

### Gameplay, finances and ownership

- Gold/XP, requirements, equipment quantities, costs, loot and damage are server-derived. Client reward/cost fields do not override them. Actor identity comes from the authenticated session.
- Character locks and database transactions serialize purchases, sales, combat, skill allocation, ally changes and grants. Per-account command receipts bind UUIDs to canonical intent; matching retries return the committed receipt and changed payloads cannot reuse it. Quantity/currency bounds prevent negative balances and overflow.
- Quest equipment purchases re-read shortages/prices/gold while locked and charge only missing copies. They consume no quest Mana and grant no quest completion; a distinct validated Quest action is required. Land quotes use saved FIFO acquisition costs/rates for sale and current authoritative successive buy prices. Max/projection controls only display server calculations.
- Land shared-cycle settlement, fractional first periods, offline accrual, separate upkeep/reserve accounting and equipment suspension retain their Phase 4.3 rules. Browser timers never credit gold; purchase previews do not move the shared clock. Existing hourly/payment regression tests remain in the full suite.
- PvP retains normal Spirit/Health/range/Calling eligibility. **No artificial repeat-attack cooldown exists by design**; this review verifies the intended resource/eligibility checks rather than adding a new delay. Pair loot diminution, protected Vault balances and development-rival daily gold/full-XP budgets remain. Eligible victories still earn at least 1 XP under the existing progression rules.
- Bounty escrow, one active target, 50 placements/rolling 24 hours, expiry/refund, finishing-only atomic payout and one bounty Kill/Death are unchanged and regression-tested. Player-funded bot bounties cannot mint funds; bots never initiate attacks or claim/place bounties. Creator/self restrictions and concurrent-claim safety remain.
- Player-profile access exposes only the existing public character subset. Private battle reports, receipts and achievements remain owner/participant-bound. New internal inventory FIFO refund steps are deliberately omitted from public profiles.
- Comments/broadcasts remain escaped plain text with persistent rate limits, reporting, owner/author removal and terminal moderation; no bots fabricate social messages. Social posts/achievements/tutorial steps award no gold or XP.
- Recruitment retains consent for real players, explicit development-only automatic bot acceptance, uniqueness and participant/capacity checks. No new administrator gameplay power exists.

### Deployment, initialization and authorized adjustment

- The production image builds from the lockfile, compiles TypeScript and runs as non-root with development tools/source/env/backups excluded. Health checks query PostgreSQL. One replica is retained. No database port is published in the isolated container checks.
- Production startup requires schema 017 and installed immutable catalogs before listening. It never initializes or migrates a database. Controlled pre-deploy migration keeps the existing transactional/advisory lock.
- For the initialized private-alpha realm, first Phase 4.4 upgrade refuses to migrate without `KINGDOM_RESTORE_TEST_DATABASE`. That name must identify a different already-restored `*_restore_test` database at the private host. The checker never opens a live pool; it requires 450 bots/accounts, compares old business rows, applies migrations only to the copy and verifies replay. The pre-deploy runner proceeds to the live pool only after success.
- The `gray` grant is a separate CLI, never a web endpoint or startup/migration branch. Railway private-alpha metadata/private hostname checks, explicit confirmation and exact inspected account UUID guard the operation. The actual authority is the owner's authenticated service shell; metadata flags are deployment checks, not a substitute for Railway account authorization.
- The grant uses a fixed authorization ID, advisory/character/wallet locks, ordinary financial ledger and immutable operator journal. It credits only 50,000 spendable gold once and rejects wrong/missing identities or a purse that cannot fit the entire grant. Tests use an unrelated synthetic `gray`, not the live account.

## Owner must verify before widening access

These are **unverified live infrastructure gates**, not verified facts about the owner's service:

1. PostgreSQL has no public TCP proxy/exposed port; game uses the intended `*.railway.internal` URL and existing data volume. Access is restricted to authorized Railway project operators. Private-network PostgreSQL TLS behavior matches the provider; do not disable certificate verification or add unsupported TLS flags.
2. Production branch/image, `NODE_ENV`, exact HTTPS `APP_ORIGIN`, port8080, health/restart settings and one replica are correct. No broad trust-proxy/header override or alias domain bypass is enabled. Test real registration, login, CSRF rejection, logout and an existing account after manual deploy.
3. Historical `KINGDOM_ALPHA_INITIALIZE`, `KINGDOM_DEV_PASSWORD`, `ALLOW_DEV_PROVISIONING` and `RUN_MIGRATIONS` variables are removed. Remove temporary grant confirmation/identity/reference after use; do not persist them as service startup variables.
4. Rotate any previously disclosed PostgreSQL or development-account password through an authenticated operator session. Synchronize sealed provider credentials/private references and test a **new** private connection; never paste passwords or URLs into chat/logs/Git. Password rotation itself is not performed here.
5. Take/export/hash a real consistent backup, restore it into a separate database, verify human records and all 450 bots, then run the copy migration check. Keep a recovery copy independent of `/tmp`; verify existing provider volume backup retention/access. Do not restore over the only live source.
6. Restrict the controlled cohort at the owner's access boundary, monitor authentication failures, balances, bounty flow and error rates, and appoint someone to handle reports using `node deployment/moderate.mjs` in the authenticated game-service shell as documented in the release guide. The registration page alone is not an invite gate.
7. Check provider log access/retention; no sensitive environment values/backups should be public. Application diagnostics omit database credentials and redact cookies/authorization/password fields, but the provider's own logs/secrets are outside this review.

## Remaining risks and operational limits

- No MFA, account recovery/email verification, verified-human/invite-only registration or device attestation was added. Credential stuffing, username-targeted 15-minute lockouts and multi-account collusion remain concerns for an unrestricted public URL. Existing bot and reward budgets limit per-account extraction but do not prove Sybil resistance. Keep this a controlled pre-alpha and investigate suspicious linked accounts rather than promising farming is impossible.
- Authenticated-route/global socket-peer throttles are process-local; per-identity auth counters are durable. A Railway shared proxy may group clients under one peer and throttle unrelated users. Validate expected player load; use a narrowly trusted provider edge with verified identity/rate policy before scaling. Do not switch to trusting arbitrary X-Forwarded-For. Multiple replicas need shared throttling beyond the durable login counters.
- Anonymous sessions, durable auth keys, receipts and expired quotes accumulate. Limits bound ordinary rates, not indefinite storage. Add monitored retention/archival with a separate reviewed policy; do not delete financial, battle, grant or achievement journals to reclaim space.
- The main application database role can migrate the schema. Player web routes have no administrative endpoint, but a server/credential compromise would have database impact. A least-privilege runtime/migration role split, independent backups and credential rotation are appropriate before larger testing; not silently changed on the live provider here.
- Temporary bots and the known development account are approved alpha content, not production identities. Keep their switches explicit and review disabling development features/rotating the development credential before public launch. Existing identities and histories are preserved.
- Durable achievement recognition currently scans relevant saved histories when authenticated pages/commands are processed. Added query indexes and the 450-rival fixture support the current alpha size; very large histories require measurement/aggregation rather than assuming unlimited scale.
- Native browser tests use Chromium at Android/iPhone-like widths. They are not tests on physical Safari/iOS/Android, Railway's real edge, APK/WebView or a public attack simulation. There is no APK compatibility/security claim.

No public deployment or recommendation for unrestricted release is made. The release is prepared for an owner-run, backed-up **controlled pre-alpha** after the outstanding live gates are checked.
