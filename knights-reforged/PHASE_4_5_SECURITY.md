# Phase 4.5 security and preservation review

Scope: changed application/SSR/browser code, immutable rules, additive migration 018, existing authentication/Origin/CSRF implementation, real local PostgreSQL concurrency/migration tests, native TLS browser forwarding fixtures, and production-container deployment rehearsal. No live Railway account/database access occurred. This report supports controlled alpha testing; it is not a penetration-test or production-security certification.

## Issues addressed during this iteration

- The prior attack preparation could replenish bot gold/free upkeep reserves after a daily marker. This was authorized development behavior, but it undermined sustainable exposed-gold testing. Phase 4.5 removes both paths and adds real-cost, once-per-boundary maintenance; existing journals/reserves/balances are preserved. No exploitation of the live service is alleged.
- Redundant Land preview submissions added a round trip. Removing the preview does not remove transaction safeguards: direct actions retain the same validated commands, receipts and locks; historical quotes remain owner-bound and single-use.
- Browser verification caught existing button display styles revealing the new hidden retry control, plus a deferred native-toggle panel race. The status panel now explicitly honors hidden controls, sibling closure happens synchronously, and client regressions cover closure and stale read protection. Financial receipts already prevented duplicate charges; these fixes remove misleading interaction states.
- Bounty board reads used queued simultaneous queries on one transaction client. Sequential reads and early self/sponsor exclusion remove the driver warning/unnecessary reads without changing claim authority.
- A new healing-panel balance made an old browser test's generic gold locator ambiguous. The test now selects the main balance explicitly; this was a fixture issue, not a duplicate payment.
- The local Docker disk filled during verification, preventing the disposable PostgreSQL container from initializing. Only unused build cache was removed; no database or backup was deleted. The deployment rehearsal was rerun after space was restored. Readiness diagnostics now redact the generated password and include disposable-container logs on failure.

No confirmed critical/high application vulnerability from the changed-scope review is intentionally left unresolved. This is limited to the review performed and the reported tests.

## Outstanding risks and owner actions before wider access

1. **Actual backup and migration:** create/export/hash a consistent live backup and restore to the separate private `_restore_test` database. The local fixture is not the owner's real data. Follow `PHASE_4_5_RELEASE.md`; never reset/seed/restore over the source. Verify managed backup retention and recovery access.
2. **Provider boundary:** verify Railway private networking, no public PostgreSQL TCP endpoint, HTTPS certificate/domain matching APP_ORIGIN, health/start/restart policies, one replica, secret removal and persistent database volume. Local forwarding tests do not attest to live edge settings.
3. **Secrets:** remove obsolete initialization/dev-password/general-provisioning variables. Rotate any previously exposed PostgreSQL credential privately and verify a fresh application connection. Never print connection URLs or dump contents.
4. **Abuse/collusion:** alpha cannot establish real-world account ownership; coordinated human accounts/bounty gifts or rotating opponents cannot be perfectly detected. Rate/encounter limits, escrow, Spirit and authority checks reduce abuse but are not identity verification. Monitor economics, moderation reports and suspicious repeated targets.
5. **Throttling and capacity:** persisted authentication identity counters survive app restarts; per-process gameplay/global request limits assume the configured single replica. Multiple replicas, edge DDoS control, shared proxy capacity and pool sizing need an operational review before scaling. New rules do not introduce an attack delay.
6. **Bots:** keep per-feature private-alpha flags deliberate. Exposed purses earn from real, sometimes high-tier Land rates; monitor earned income, caps and retained treasury. Disable passive rivals/optional features before public launch when appropriate. Do not erase bot rows/history as a configuration change.
7. **Devices:** responsive Chromium checks cover touch layouts and reduced motion at representative Android/iPhone sizes, not physical devices, Safari/WebKit or Android APK compatibility. Owner tests on actual Android/iPhone remain required before inviting a larger cohort.
8. **Economy:** arithmetic and accelerated no-grant level-50 playthroughs establish reachability/invariants, not long-term multiplayer balance or human retention. Review actual XP/loot/upkeep telemetry without retroactively rewriting rewards.

Retain the known Phase 4.4 image and verified source backup. Roll back the application if needed without down-migrations or deleting new journals; recovery to an older snapshot may lose later gameplay and requires an explicit owner decision. No deployment, live adjustment, public invitation or APK conversion is performed by this branch.
