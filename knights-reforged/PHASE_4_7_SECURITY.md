# Phase 4.7 security and preservation assessment

Scope: source review, synthetic populated PostgreSQL migrations, transaction races/replays, actual local HTTP/TLS reverse-proxy browsers, production containers, audio/marketplace client behavior and release-workflow guards. No live Railway credentials, database, account or deployment was accessed. This is supporting evidence for a controlled alpha, not a claim of comprehensive production security or an independent penetration test.

## Verified protections

- Existing Argon2id passwords, hashed durable session tokens, HttpOnly/SameSite=Lax cookies, Secure cookies under HTTPS, strict canonical Origin and session-bound CSRF remain intact. Codespaces' narrow documented localhost-Origin rewrite remains scoped to the configured HTTPS Codespace, canonical Referer and same-origin Fetch Metadata; forwarding headers cannot select an allowed origin.
- Logout deletes the session. Login rotation, seven-day inactivity policy, durable authentication limits and account-disabled checks remain. Returning to a marketplace after login accepts only a small server allowlist of paths; external/protocol-relative/unknown destinations fall back to Home.
- Healing, equipment/Land transactions, ordinary loot, XP, bounty escrow/refunds/claims and recruitment retain the existing server validation, sorted character locks, atomic ledger and fingerprinted command receipts. Posted prices/refunds/rewards never become authority. Replayed sales consume no second inventory and pay no second refund. Equipment resale is floored per recorded-cost copy; its rate is below cost, preventing ordinary buy/sell arbitrage. Land resale and upkeep policies are unchanged.
- An ambiguous marketplace request retains its original action ID and complete intent. Checking current authentication does not submit a purchase. A different signed-in identity is rejected locally and server ownership still governs receipts/commands. Known rejected requests can be reviewed and tried again deliberately; uncertain server/network errors retain the original pending action. No expired quote or CSRF lifetime is extended.
- Bot housekeeping is enabled only through existing permitted bot configuration, affects only registered active bots with actually due saved Land clocks, skips locked characters and uses normal settlement/upkeep. Repeated calls, restart, viewing or attacking do not manufacture gold. Vaults, holdings, equipment and identities are not rewritten. No bot-finance HTTP endpoint or one-time endowment is introduced. The owner audit is private/read-only and returns bot data only.
- XP preserves level/strength eligibility and encounter limits. The presentation's “decisive” label cannot influence the formula. The updated result is what progression credits and durable reports save; old records are untouched. Cosmetic audio/animations make no reward requests.
- Sound preferences are authenticated/CSRF-protected commands with bounded boolean/volume inputs. Audio is default off, non-looping, same-origin, gesture-unlocked and uses a bounded local replay cache. Native result sound requires a matching recently submitted action; direct historical/refresh visits remain silent. Routine gestures do not predict success. Browser-blocked playback offers an explicit tap. Reduced-motion support remains; enabling sound is a separate explicit choice.
- Broadcast moderation retains exact two-ID review, immutable-record digest, explicit owner confirmation, transaction locks, idempotent reversible hides and audit history. No cleanup occurs during migration, startup, release or this work.
- Additive migration 020 changes no pre-existing business row. Populated 019 fixtures compare all original rows, including sessions, financial histories, achievements, three guide cursors/completion states, bots and competitive summaries, then verify replay. Old rulesets are immutable; new resale/XP policy has its own ID.
- Production uses the portable non-root Docker image and controlled pre-deploy migration runner. Startup cannot initialize/migrate. Bootstrap credentials/flags cause refusal. PostgreSQL remains private. Health exposes only readiness, public rules version, release name and a validated optional commit SHA.

## Confirmed defects fixed

1. **Quantity menus replaced by the Level refresher.** A shared `data-level` attribute identified both an entire quantity control and the player's Level text. Background `realm-state` updates replaced the control's children. Requirements now use `data-required-level`; the browser regression dispatches a real server-state response and verifies that the actual inputs survive. This was a UI correctness defect, not a reason to weaken sessions or CSRF.
2. **Unsafe recovery experience after interrupted/expired requests.** Native error navigation lost marketplace context; quantities were not durable. Shared persistent safe selections, current-state revalidation, explicit reauthentication and same-ID pending retries now preserve context without authorizing stale or duplicate transactions.
3. **Hidden retry buttons styled as visible.** Generic button display rules overrode the hidden attribute. A final scoped `[hidden]` rule restores the intended semantics, tested on the actual Buy More interface.
4. **Unseen bots' displayed finances stayed stale.** Income was durable but lazy. Bounded ordinary background settlement makes it independent of player profile views. No financial grants or historical edits are used as a substitute for settlement.

No confirmed critical/high-severity vulnerability was identified by this scoped review. That statement does not establish the absence of vulnerabilities outside the tested paths.

## Release automation safeguards

- Only a manual run on protected `release/production`; feature pushes run unprivileged tests only. A default run is a backup rehearsal. Exact production-commit CI, correct default-branch workflow availability and complete owner setup are required.
- GitHub checks the sole owner's required environment review, disabled administrator bypass and a single exact allowed release branch before the credential-bearing job. The owner performs one explicit environment approval. Railway GitHub autodeploy must separately remain disabled; the workflow records the owner's attestation rather than claiming to inspect an undocumented provider setting.
- Project-scoped token and dedicated SSH key live only in protected environment secrets. They are exposed only to the approved operator steps, after dependency/tool installation. Actions and Railway CLI are pinned. Strict SSH host verification is mandatory. No database password or connection URL leaves Railway.
- The running game/private PostgreSQL identity is verified, capacity checked, backup exported and hash/archive verified, then the independent export is encrypted to an offline owner-held age identity. A separately downloaded retained artifact must match before promotion. Plaintext runner files are private and removed. Private restore databases/source dumps are retained for review, never automatically overwritten or dropped.
- The actual candidate's compiled migrations and locked runtime dependencies test the separate restored database. Every old business row is checked via bounded cursor hashing, all 450 bots required, and replay must be unchanged. A failure stops before real migration/deployment. No seed/reset/dev provisioning/grant/moderation operation exists in the release path.
- Staged non-secret release markers use `--skip-deploys`; only the deliberate subsequent CLI call deploys. Post-deployment requires the exact commit/release health result, installed schema, saved initialization/450 bots/no bootstrap secrets and a working login page. Failure stops without an automatic database rollback.

Local containers verify native PostgreSQL export/checksum/restore and copied-data migrations. Unit guard tests inject corrupt/truncated backups, incorrect branches/reviewers and failed preservation reports. actionlint verifies both workflows. Authenticated GitHub protection-plan behavior, Railway SSH/token permissions, independent host-key trust, actual artifact retention and an end-to-end provider promotion remain owner setup/rehearsal checks; they were not performed here.

The first GitHub run passed the full suite and audit but failed its sound preview under the runner's automatically selected system Chromium. CI now selects installed Google Chrome explicitly and checks actual AAC decoding before the interaction suite. This is a test-browser compatibility correction, with no gameplay or credential changes; codec failures remain fatal rather than being skipped.

## Outstanding risks and acceptance gates

- Complete the owner rehearsal and offline-key decryption check before approving promotion. Keep a durable independent encrypted backup and Railway-managed backups. GitHub artifacts expire; `/tmp` is not durable storage. A restore consumes capacity on the same PostgreSQL volume, so monitor it and review specifically named old test copies before any cleanup.
- Use a dedicated least-privilege Railway automation identity. SSH keys may carry broader account/workspace privileges than a project token. Protect workflow edits, environment secrets and the release branch; a compromised approved release runner can execute privileged operator actions. The design does not pretend to eliminate that administrative trust boundary.
- Actual live bot portfolios were unavailable. The read-only audit can reveal overdue clocks, paused upkeep or legacy portfolio drift. Do not silently provision or grant capital to “fix” an unverified live condition.
- Physical iPhone Safari and Android Chrome listening, browser audio interruption and OS tab-eviction behavior require device acceptance. Headless Chromium AAC/gesture tests and viewport checks are useful evidence, not native-browser/APK certification.
- Existing alpha anti-farming limits remain, but deliberate multi-account collusion is not comprehensively solved. Existing request throttling remains partly per-process; keep the supported single replica until shared throttling is designed and verified.
- The two live Gray / Development Night broadcasts are still unreviewed. Only the owner can approve the exact reviewed immutable records for reversible moderation. Release deployment must not clear them automatically.
- Wider distribution should wait for provider health/session smoke tests, managed-backup confirmation, recovery-key retention and the device checks above. No public deployment recommendation is based solely on green automated tests.
