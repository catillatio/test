# Beta theme — route and state coverage

This inventory comes from `src/app.ts`'s actual `render()` callers, `src/http-contracts.ts`, and the current EJS templates. It distinguishes rendered screens from redirects, JSON endpoints and an unreachable historical template. No route, race selection or product flow was added for this review.

The browser harness uses the default Iron & Brass application and a separately constructed, internal `legacyTheme: true` application against the **same disposable schema**. The baseline option is limited to test + loopback. Every named live case is exercised at **320, 390, 430, 1024 and 1280px**, with decoded images, font/layout readiness, matching content/forms/links/approved art, header fit, five-tab navigation where authenticated, and no horizontal overflow. Original 80 representative comparisons and 35 glow-centering cases remain. The default run covers all five widths; mutually exclusive `--mobile` and `--desktop` CI modes partition the same matrix into three mobile and two desktop widths and write distinct evidence files. The core victory also checks that the existing 44px repeat-attack action is visible above the fixed navigation without scrolling. Both saved reports validate displayed loot, bounty payout and damage against their authoritative synthetic battle records and retain valid `dt`/`dd` groups.

## Historical template, not a live screen

`trade-confirm.ejs` is the twenty-second declared template, but has **no current `render(..., 'trade-confirm', ...)` caller and no reachable quote-page route**. The existing `scripts/check-project.mjs` already renders its buy/sell template contracts in isolated EJS fixtures. Current Land purchase/sale commands use their real catalog controls and redirects, covered above. The UI work does not invent a public route or make the old template live to inflate coverage.

## Actual transitions and native interactions

The browser executes resource disclosures, equipment inspection/Close, market Buy/Sell tab keyboard navigation, a real market purchase, a broadcast, tutorial resume, Vault deposit/withdraw with conserved balances, persisted Settings sound autosave, the no-script notification-read form with a newly delivered personal event, and the complete **Register → Tutorial → lesson 4 Calling → Sign Out → Sign In → Home** journey. Those commands are explicit test actions after the unchanged-business-rows comparison, using synthetic accounts only. There is no new signup/race/Calling flow.

Production-mode SSR against the disposable fixture uses `loadConfig({ NODE_ENV: 'production', APP_ORIGIN: 'https://realm.example.test' })` and `app.inject()` on the same disposable DB. It verifies default-new CSS on all reachable GET/error templates and the actual bounty-preview/login-error/registration-error POST views using the correct HTTPS origin and existing CSRF contract, without overriding secure production configuration or contacting production. Bounty preview is nonfinancial. Existing session, authentication-attempt and quest-region preference writes occur only in the disposable fixture; the unchanged-business-rows comparison excludes session/preference tables and precedes the explicit native commands.

Redirect contracts are checked separately: public/signed-in `/`, signed-in `/login` and `/register`, signed-out private routes and self public-profile URLs. They are navigation transitions, not additional screens.

## JSON-only endpoints

These routes return JSON rather than themed HTML: `/healthz`; `/api/v1/me`, `/opponents`, `/champions`, `/achievements`, `/notifications`, `/bounties`, `/bounties/quote`, `/feed`, `/land`, `/battles/:id`, `/players/:id`, `/players/:id/combat`, and `/players/:id/tales`. The harness checks status, JSON content type and expected response keys using authenticated fixture identities. Existing command API responses and authorization remain unchanged.
