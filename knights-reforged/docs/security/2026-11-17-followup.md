## Newly identified source-level availability concern — requires reproduction

**AVAIL-01 — guest-session growth (potential Medium, CWE-400; impact not verified).**

`src/app.ts` creates a new anonymous session for a GET or HEAD request without a valid session (except static assets and health), and `src/auth.ts` writes that guest session to PostgreSQL with a one-day `expires_at`. `findSession` excludes expired sessions on lookup; an inventory search did not find an automatic `DELETE FROM sessions WHERE expires_at...` pruning path. Logout and explicit account-erasure operations delete only specific sessions. An unauthenticated client that discards cookies can thus generate repeated persistent guest-session rows, subject to existing rate limits. A distributed request stream could grow the table and increase disk/backup overhead.

This is a verifiable source path, **not** a measured attack, severity certificate or live sessions count. Before a fix, use a disposable PostgreSQL fixture to (1) confirm row growth for independent cookie-less requests, (2) characterize any existing database-side TTL/maintenance job, (3) measure contention and disk effects, (4) test a bounded race-safe cleanup or deferred guest-session strategy preserving first-party CSRF and existing sessions. Do not delete live sessions or introduce an unreviewed background cleanup.

## Other checks and limits

- Authenticated command paths use server-derived account IDs, Zod intent parsing, bound SQL parameters, transaction locks and durable idempotency receipts. `/account-deletion/requests` requires a fresh credential check and shared CSRF hook. The candidate's centralization must pass hosted tests.
- The dynamic SQL in `src/competition.ts` derives identifiers, sorting and filters exclusively from fixed source-defined champion categories, with cursor fields validated by Zod. No user-controlled SQL identifier interpolation was found there.
- Twelve browser JS modules checked contained no `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `eval` or `new Function` sinks. Existing same-origin API requests and sessionStorage/localStorage use were inspected; this does not certify all UI code.
- Nine current GitHub workflow YAML files were screened for obvious major-tag Actions and secret-echo commands; none found. Protected release authorization and digest pinning remain mandatory.
- Android's WebView shell enables JS but disables file/content access, blocks mixed content and SSL bypass, uses a strict exact HTTPS game host and does not expose a JavaScript bridge. Same-origin-to-external redirect chains and actual device/provider behavior were not dynamically tested.
- **Functional, not security:** `GET /api/v1/bounties` calls `loadBountyBoard` without the NPC-sponsored bot-target visibility argument, unlike `/game/bounties`. This can hide legitimate NPC-sponsored bot contracts from API clients. Review as a separate scoped gameplay fix rather than mixing into the security rollout.
- Live PostgreSQL PUBLIC grants/default ACLs and operator roles, Railway edge/IP behavior, current container OS-layer advisories, actual Play device behavior, and true live request timings were not independently verified.
